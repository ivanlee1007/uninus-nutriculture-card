## 1. 可操作使用者路徑
1. 外部 HA automation 呼叫既有 `uninus_nutriculture.start_flow`，payload 不變 `{config_entry_id, request_id?}`；或操作 registry 對應的原生 `flow_run` ON。兩者繼續進 Controller.start → FlowCoordinator.start 同 gate，沒有新 scheduler、腳本、19 排程或 8 滴灌腳本匯入。
2. `accepted:true,run_id` 只表示已受理；新 `get_result_v1`（HA response service）或新原生 result_status sensor 查 `current_run`／`last_result`，依 entry_id + epoch + run_id 關聯，不把 return 或 switch OFF 當完成。訂閱原生 bus `uninus_nutriculture_result_v1` 作即時提示，斷線後 GET 收斂，事件不是 durable queue。
3. 到「設定→裝置與服務→該槽→選項→通知管理」，或 shipped Card 新 `result_entity` 選取器與通知面板，以 native provider 下拉、notify entity selector、事件複選、cooldown、Save/Cancel 設定。預設 disabled／無 provider／無 target／事件空集合。開面板、GET、取消、重新整理、Save 都不發測試通知、不致動；本 slice 不提供 test-send。
4. 通知的 ACK 按鈕只將指定 event_id 標為已讀，不消除 fault、不 reset、不變 master、stage、quality 或 permit。provider 完成只表示 handoff_returned，不稱收件者已收到。完成本輪也不代表 quality 合格或 permit=True；灌溉唯一權威保持既有 quality_v1／permit binary_sensor。

## 2. Additive wire 與權限（P4C_API_SCHEMA.json 為 exact keys）
不改 S1–S5、recipe_v1、quality_v1 producer/consumer strict DTO，不建立 S6。新 `result_v1` 用獨立 sensor（unique_id=`{entry_id}:result_status`）與 `get_result_v1`；sensor state 為 current_run.state，無 current 為 idle，v5 以外為 unsupported。整個 extra_state_attributes 與 GET DTO 同一已快取 immutable snapshot；不是加欄到舊狀態。新 `notification_v1` **僅 admin 私有 WebSocket** 與 Options shared execute，不走通用 call_service，避免 HA 自身 call_service 事件廣播私有設定。

### Result
- `get_result_v1`: HA SupportsResponse.ONLY；strict `{config_entry_id}`。ACL 使用既有 control_auth.authorize：有 user_id 必須 native active admin；無 user_id 僅既有 Core 內部 automation context，維持既有 start_flow 政策，不增加 human bypass。公開 sensor/event 不主張 admin 秘密，皆為 allowlisted 最小操作投影，不含 context/user_id/request_id/exception/provider/target/source Entity IDs/配方名。
- `schema_version=1`; `config_entry_id` 是原 native entry ID opaque string；`epoch` 每次 entry setup 產生 32 lowercase hex，不等於 quality epoch；`observation_revision` 0..2^53−1，在本 epoch 實際投影改變才 +1；溢位換 epoch 並完整重新投影，舊 request fences 失效。notification_revision 不隨 run 改變。
- run_id 沿用 FlowCoordinator 既有 uuid4.hex，不另造 id；run.epoch 是受理 epoch，event_id=`epoch:sequence`，sequence 1..2^53−1，重入 publish 不重新分配。event.sequence 可因投影無事件的變化而少於 observation_revision，兩者不等同。
- GET 不呼叫 flow.state/refresh、quality.dto/observe，不做 provider lookup、Store load/save、publish、時間採樣、計數、事件分配或 expiry maintenance；只在 auth/lifecycle admission 後複製 cache。相同 revision 的 GET/native/event.run bytes 與 transition_at 相同。UTC RFC3339 +00:00 timestamps 在轉移一次擷取，非每次 GET 重畫。elapsed、cooldown、queue TTL 用 monotonic；wall rollback 不重送、不提早成熟；annotation timestamp 可倒退，順序只看 epoch/revision/sequence。
- `current_run` 持有 accepted/running/stopping 的一輪；`last_result` 僅一筆已閉合 terminal run。terminal 時 current=null，last_result 換成此輪，無 current grant 語意。run.started_at 可 null（整輪受理後尚未實際 stage start；refill 無需開泵即可完成亦可能 null）；run.finished_at 僅 terminal 有值。沒有用舊品質資料合成結果。
- **不持久化 last_result 或 active run**：只保留本 runtime 一筆至下一 terminal／unload。restart 新 epoch/current=null/last_result=null/latest_event=null，不恢復／補跑／補送；Card 舊 epoch 結果立即灰化不作 current，使用者可明確看到重啟後無本輪結果。這是刻意保守工程選擇，不假稱有跨重啟歷史；完整歷史留 P5。
- 不新增 rejected event 或 admission DTO；原生拒絕仍原 transport，未受理零 run/event/result mutation。重複 native ON／同 request_id receipt 不產生新 accepted/event，也不改既有去重期限；本案不修 P3 receipt 行為。

### Native result/event 狀態機
accepted → running（第一個 actual dispatched started_at）；尚在 delay/condition/resource wait 時維持 accepted 或 running，stage.phase 具體呈現等待。正常停止／fatal 首次觀測先 state=stopping，closure=pending，保留最後 failure reason；停止未確認為 state=stopping,closure=unconfirmed,reason=stop_unconfirmed。**不得只看 f.active=False、f.outcome=completed 或 control.flow_state=fault 就終結。**
完整 closure 必須：(a) f.active/stopping false；(b) c.running false，無 leases/late_on；(c) c.on_task/off_task、四 stage.operations 全 done；(d) 四 owner.owns_io false 且 cleanup task 無未完；(e) accepted 當時捕捉並持續追蹤的所有輸出 registry identity 仍可證同一設備且 state 明確 off。binding 被移除或 Entity 替換不能消除舊關閉義務；unknown/missing/rebind 均 unconfirmed。使用原生 registry resolver 的 identity proof，不比較猜測 entity 名稱。
closure confirmed 後才可出 terminal：任何 fault 或 stage fault→failed；否則 f.outcome=aborted／generation 被撤銷→stopped；否則 f.outcome=completed 且所有 accepted-enabled stages result=completed→completed；含 enabled skipped_weekday/blocked_dependency/aborted 或無有效階段→incomplete。disabled stages 不當成功，也不單獨阻已選其餘 stages 的 cycle completion；是否必要完整由 P4b 決定。fault 持續鎖定不妨礙已證閉合的 failed result，closure 檢查不可直接重用會因 fault/master/quality 早退的 Quality.guard。
- accepted/running/stopping/completed/stopped/incomplete/failed 是同名事件；stop_unconfirmed 在首次 unconfirmed episode 發一次，可於晚 OFF 閉合後再出 failed，絕不出 completed。fatal 最初只出 stopping + safe reason；failed 僅閉合後發。stop 通知來自 stopped，不是 OFF request。超時可在尚未閉合時事件 stopping 的 reason=flow_timeout 等，notification dispatcher 分類成 timeout，勿等 provider 才 OFF。
- Tick/publish 重複數十次相同狀態必須 idempotent；同一 event_id 最多 enqueue 一次。stage 進度投影更新可 +revision 但不重播 run lifecycle event。新的 terminal 後收到既有 late callback 不能把 terminal 升級 completed；若先前 closure 証明失效，維持 failed／暴露 stop_unconfirmed，而不是逆轉成功。
- event envelope exact fields 含 `run`（可 null，idle alarm）、`kind`、`reason`、timestamp 與 identities；bus 使用新 Context() 不攜帶原 user context。GET.latest_event 只是一筆最新事件，不重播或恢復遺失事件。consumer 以 event_id 去重，斷線遺失 intermediate 是真實限制。

## 4. 私有通知 API、Store 與 UI
僅下列 WS type：`uninus_nutriculture/notification_v1/get`、`.../save`、`.../ack`；以 native websocket_api authenticated connection、require_admin 及 shared human authorize（recipes.authorize）再次查 user。Options 使用 context.user_id 呼叫同 shared execute，不經 ServiceRegistry。schema 的 WS id/type 為 transport，不持久化。每次 async auth/Store await 後驗 entry object、runtime owner、active、Core lifecycle、epoch、human principal 仍存活/active/admin/not system_generated；最終 effect 前 no-yield fence。不得信任客戶端 is_admin 字段，owner ID 必須 primitive nonempty str（不做 String(object) coercion）。
- 存取本槽 private Native Store `uninus_nutriculture.notification_v1.{entry_id}`，version=1，atomic_writes=True；setup 可讀既存檔，缺檔以 virtual disabled defaults，不建檔。只 accepted save 建檔；GET/ACK/navigation/rejection 零 Store writes。result 不用 Store。Store errors、legacy/corrupt config quarantine 為 disabled/unavailable 並給固定 code，不回 raw。
- Store document exact `{schema_version, config_entry_id, revision, policy}`；policy exact 見 P4C_API_SCHEMA.json。revision 獨立 0..2^53−1；每次成功 save +1（包含相同 policy，避免 swallowed native save 與等值舊檔混淆），overflow 拒寫 notification_conflict。save 用 expected_epoch+expected_revision CAS；無效、cross-entry、revoked、CAS 拒絕：private disk bytes/runtime policy、result/events、所有 options/fault/stages/quality/permit 與 actuator calls 均不變。
- 保存採 entry 私有 mutation lock；不持 tank/control/safety locks跨 await。native Store save + physical envelope readback 驗 candidate revision/entry/schema 完整相等再 publish private cache；writer吞錯、readback失敗或 cancellation 只能回 storage_failed／indeterminate，不能宣稱 committed；close mutation admission、drain 真正 I/O再 release lock，indeterminate 重開 reload reconcile，不自動 retry/rollback 造成覆蓋。若 disk 已提交而 caller timeout，fresh GET 必須先 setup/explicit reconcile，不能承諾被拒絕一定未寫；將 pre-admission rejection invariance 與 admitted I/O indeterminate 分開。
- 設定不寫 config_entry.options，避免 QualityCoordinator.settings fingerprint 將通知保存誤認 control settings changed／撤銷 permit。新 Store 不加 quality_v1 欄位，通知 enable/save/ack 成功或失敗不能改 P4b authority。
- private GET 回當前完整 policy + availability + bounded delivery records，不放 public sensor。get 可從 cache 判 availability；provider registry/state事件更新 cache，GET 不查 provider／不觸 I/O。下拉由本機已載入 notify entity catalog（admin 私有）生成，無外網 discovery，無 credentials／收件者自由輸入。無 notify entity 時仍可選 persistent_notification；不聲稱 legacy notify service-only 整合受支援。
- nativeOptions `notification_management` 與 quality/recipe 一樣在 init 提早分支，不保存同頁其他設定；表單 native selectors：enabled Boolean，provider Select，target EntitySelector notify 單選（PN 時隱藏），events multiple Select，cooldown Number integer 60..86400（工程 default 300s）。enabled=true 必須有 provider 及非空 events；notify_entity 必須有一個有效實體；PN target 必須 null；disabled 允許保留合法設定但不 dispatch。
- Card 新獨立 result_entity selector（registry取 entry 身份，不猜槽名）；可 read-only result 卡，沒有 admin user／服務能力時所有私有設定與 ACK 隱藏或禁用，不讀 private get。私人資料每次 principal id/role/active、entity/entry、connection/callWS、epoch、owner token或 generation 改變即 purge；dirty draft 不跨 owner。op 捕獲 entry/epoch/owner/principal/ws/connection/generation，任何 late reply 不復寫新頁、不得回舊 target。save→private get readback 同 revision/policy 後才顯示成功；user、role、owner 同 ID也須 primitive role equality。結果權威只 native result DTO，quality/permit 仍原 P4b面板。

## 5. Provider 能力 allowlist 與 privacy tradeoff
僅 `provider=null|persistent_notification|notify_entity`；絕無 service/action/template/url/script/command/device/area/label 任意欄位、任意 kwargs、callable 或 notify legacy service 名稱。不能用 switch.turn_on／integration.reset_fault 當通知。notify target 只能單一 `notify.[a-z0-9_]+` 並存 registry stable registry_entry_id、unique_id/platform/config_entry_id identity proof（後端生成 binding，不信任 client），重命名仍認同一 row，刪除重建同 entity_id 拒送；相同目標可供多槽通知但 envelope隔離。selection不存在／disabled／unavailable → save 拒 invalid_provider；保存後能力消失 → queued jobs provider_unavailable，不自動換收件者／fallback。
**隱私重要決定**：SDK ServiceRegistry.async_call 會發 call_service event，因此即使把自訂 result payload清乾淨，直接 `notify.send_message` service仍會公開 native target。為符合本案「public native sensor/event 不含通知target/provider config」，adapter 不使用 ServiceRegistry dispatch：PN 以原生 `persistent_notification.async_create(hass,message,title,notification_id)`；notify 用已載入 EntityComponent.get_entity 得到經 identity驗證且 isinstance NotifyEntity 的實體，僅 `async_send_message(message,title)`；只有 supported_features 含 TITLE 才傳title，否則傳None。正常返回且 fence仍有效可用原生 `_async_record_notification()`記錄通知 timestamp（官方notify entity文檔列出此接點）；typed adapter seam 必列 pin compatibility tests，不能散佈 SDK private use。此為使用 HA 原生 notify entity能力，不是通用 service runner；不支援 legacy service-only provider 是明示能力邊界。
公用訊息只由 backend 固定 zh-Hant/English 模板生成，title<=80 Unicode scalars/message<=512 scalars，NFC、拒 lone surrogate/C0/C1/bidi control；無用戶模板、槽名、entity ID、target、URL、exception或外部文字插值；只有 allowlisted kind/reason、opaque run token及時間。PN notification_id 由 entry+event opaque hash導出固定長度，不含私人 provider設定。公開 integration sensors/events/結果 API不揭露 provider/target，通知選擇仍存 HA admin私有儲存及 WS；此privacy保證範圍為本integration新公開sensor/result/event與不產生含私有config的call_service；native notify實體本來可見，其自身state_changed可含該實體ID／最後發送時間，不宣稱HA原有registry、provider本身entity／事件／日志對其他HA使用者保密，也不聲稱對 HA host admin/backup/已選provider隱藏。所有被選通知本來就是使用者同意的訊息出口，不能保證第三方惡意 provider 不做旁效或 blocking event-loop；只允許 HA native notify contract，不授其他權限。
錯誤 exact allowlist：private delivery code `provider_unavailable|provider_failed|provider_timeout|queue_full|cooldown|expired|cancelled|revoked|storage_failed`，未知與空異常統一 provider_failed，不做已知prefix匹配、不存str(err)。public run reason 只 control._FAULT_CODES 的 exact codes及 schema 列表；未知統一 operation_failed。notification error 絕不寫 Controller.fault；舊 fault hydrate／setter exact allowlist 保留。

## 6. 有界 dispatcher／ACK／lifecycle
每 entry 一 worker + queue最多16，總 integration同時native dispatch最多2；each entry in-flight最多1。native task 保有單一 tracked slot；provider timeout=5s，queue TTL=60s（單調時間），cooldown default300/range60..86400，dedupe最近64 event IDs，private ledger最多32、ACK set最多32，均工程 resource defaults 非農藝值。非終結告警用 (entry, alarmkind, episode) 去重／cooldown，run lifecycle用 (entry,run_id,kind)；不同 run start/stop也受同kind cooldown，不自動補送被抑制事件。terminal/stop_unconfirmed優先：queue滿淘汰最舊非critical；若全critical，拒新job queue_full並保留result event，不能無界加task。沒有 retry、沒有 restart replay、沒有 cooldown到期補送。
Safety owner先執行／安排OFF，observer只同步入queue，不 await notify、Store、ACK、queue可用性或provider semaphore。worker永不持pump lease／control/tank鎖。timeout以 wait 從親task切離，標 provider_timeout並cancel一次；若provider忽略取消或executor仍running，此slot保持quarantined，不再開該entry新native task，直到真正settled，避免不合作provider造成無界tasks；global2 slots亦保持直到真settled。不能聲稱5s能殺掉執行緒、撤回已寄訊息；provider synchronous堵塞event-loop不可由async timeout保護，屬 native provider trust boundary。
unload/STOP先同步關通知admission、++generation、清queue、cancelworker，隨即走原 control.shutdown/OFF，不等待native provider settled才安全停止。late native ack只 retrieve exception／釋放slot，owner/epoch/entry已換時不更新任何result、fault、master、stage、quality、permit或新owner ledger。活躍run結果若unload前未閉合不假造terminal／成功通知；restart不恢復active run。原卸載因OFF未確認失敗時仍須保持通知closed，重載不可偷偷啟用補送。
ACK strict `{entry,epoch,event_id}`只針對本runtime ledger 32內事件，未知／跨槽／舊epoch拒 notification_not_found，不接受provider callback、webhook或通知button任意action。ACK只私有memory，不調用 persistent_notification.dismiss，不取消安全，也不宣稱外部通知已撤回；前台清楚寫「標為已讀（不復歸）」；已讀記錄不重發。

## 8. Parent 一次工程凍結：以下補充優先於提案舊句
本節與同目錄 `P4C_API_SCHEMA.json` 是後端／Card共同凍結契約；不是產品驗收、review APPROVED 或已交付。P4c repair仍0/2。
