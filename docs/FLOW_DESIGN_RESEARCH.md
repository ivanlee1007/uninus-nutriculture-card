# 彈性流程編排、階段星期與外部觸發：可行性研究

> 2026-11-03｜研究／設計修訂，**尚未實作**。P1 仍只做影子監測與 Number 調參，沒有本文的流程編輯器、Switch 或啟動服務。本次不修改 Python/JS/測試/CI，不呼叫任何 HA 控制，也不部署。
>
> 使用者已明確要求：階段順序／重疊與各階段星期由使用者調整；「何時啟動整輪」由外部排程／HA 自動化負責，本整合提供外部啟動入口，不建立排程器。移除獨立 `stage_link` 開關及下列精細時序政策屬本研究的**建議方案／待確認決策**，不誇稱已獲核准或已完成。

## 1. 結論與範圍修正

| 問題 | 研究結論 |
|---|---|
| 子開關與階段鏈結有無重疊？ | 抽象用途不同：子開關決定「做不做」，鏈結決定「是否自動接下一步」。但使用者可編流程後，鏈結已由流程關係表達，獨立二元開關會與編排重複並增加矛盾狀態。建議保留總開關＋四子開關，以編排＋整輪/單階段操作取代 `stage_link`；是否保留相容簡易模式待確認。 |
| 能否用 UI 任意調整時序？ | 可行。推薦「可排序階段列＋開始方式/相對延遲/條件＋並行組＋流程預覽」，不是只做拖曳換順序。由後端保存並執行有界、具型別的流程依賴圖；UI 不計時控制。 |
| 每階段能否有不同星期？ | 可以。每個階段都有星期一至日複選，與其子開關、順序分開。星期僅判斷某次啟動是否允許執行該階段，不自行產生排程觸發。 |
| 是否要內建排程與旁支管理？ | 不要。按使用者最新指示移除內建時間/cron/日曆編輯、排程匯入、外部 automation/script 管理。提供原生 HA 整輪啟動服務與狀態結果即可；安全等待、脈衝及期限仍由本整合管理。 |

## 2. 三種控制維度與鏈結重疊

1. **總開關**：允許本槽運行，或停止並拒絕所有本整合的新控制。不是「開始一次」。
2. **子開關**：某個階段是否納入可執行集合，不決定順序、不觸發工作。
3. **流程編排**：階段在整輪中何時、依何事件／條件啟動，是否允許重疊，以及其相依關係。

舊 `stage_link` 的 ON/OFF 是簡化的第三維。若同時保存「編排要求接續」與「鏈結OFF禁止接續」，就出現兩份相同權威，需要規則解釋誰優先；與其增加這個覆寫層，建議用以下清楚入口：

- **啟動整輪**：依目前已保存的流程計畫、子開關、星期與安全條件執行。
- **啟動單階段**：只執行明確指定的階段，不隱含接續；仍檢查總/子開關、星期及安全 gate。
- **停止本輪／緊急停止／復歸**：保持分開，不因重新開啟 Enable 就續跑。

P1 沒有 `stage_link` runtime 設定，不存在已發布 P1 使用者必須遷移的鏈結資料。原站的舊鏈結能力可作為新流程樣板的來源，但不直接改寫原站。是否額外提供簡化模式屬決策 R01，不同模式也必須共用同一份流程模型，不能形成兩套互相矛盾的儲存設定。

**不等價處必須明說：**舊stage_link OFF也可被理解成持久禁止任何多階段執行。改成兩個啟動按鈕只取代路由選擇，沒有保留這個持久禁止權限；因此不能說是完全等價的整理。若使用者需要這道獨立禁止，仍是不同功能，需保留一個明確多階段許可或保留舊語意。R01需由使用者選擇，不得自動刪除。

## 3. UI 方案比較

| 方案 | 能力 | 限制／成本 | 建議 |
|---|---|---|---|
| A. 單一拖曳排序列表 | 易懂、手機友善，改串行順序 | 無法完整表示重疊、條件、分組與相對時間，不足以單獨滿足本需求 | 可作簡易操作，不作完整規格 |
| B. 階段列＋開始條件＋並行組＋預覽 | 可表達串行、同時、相對延遲、感測條件與每階段星期；可用下拉選單/按鈕支援手機與鍵盤 | 需明確依賴語意與後端驗證；時間軸為計畫示意，非實際完成預測 | **推薦優先實作** |
| C. 自由節點畫布 | 進階關係直覺，可呈現更複雜依賴 | 手機/可及性與連線編輯較難；容易產生循環、死鎖與不安全組合 | 可後續增強，但不是首版必備 |

Home Assistant 官方已提供順序、並行、等待條件等編排概念及 UI；這支持概念可行性，但不代表把既有 HA 私有 script editor 元件直接放進 Card 就能穩定使用。本專案仍需自己的受限 schema、後端執行器與完整驗證，不能把一般 `parallel` 等同於安全馬達仲裁。[S2–S5]

- 拖曳排序之外提供上移／下移、並行組與依賴下拉選單；行動版改為逐列編輯，不依賴拖曳操作。

- 保存/預覽絕不啟動設備；未保存草稿不能影響執行。版本不符或儲存失敗保留草稿並提示，不用默默覆蓋目前設定。

## 4. 可編時序模型與安全界線

### 必須可表達

- 整輪開始即啟動。
- 前一／指定階段**完成後**，再等待可調相對時間。
- 與另一階段**同時開始**或在同一並行組內執行。
- 指定階段**實際開始後**，等待可調時間並滿足已綁定感測條件。
- 感測條件已成立時能立即評估，不誤用僅觀察未來邊緣的 wait-for-trigger；未成立則等待，受可調／安全最大期限約束。
- 補水→加養→加酸不是固定配方。使用者可以配置不同順序或重疊；不合法的組合必須指明相依／設備衝突原因，而不是暗中改回原始流程。

「任意」是使用者可重排作業關係，不代表可繞過最低液位、循環/混合前提、酸/養泵限制、物理輸出互斥、單次/累積劑量與最大期限。若兩個同時工作的階段爭用同一實體泵，實際啟動須經仲裁；畫面分開顯示「計畫並行」與「實際等待資源」，不能承諾硬體必然同時執行。

### 建議的有界模型（待 R02 凍結）

- 首個可用版本至少支援四種階段各一個節點、可變順序、並行、相對延遲及條件依賴；不是只支援串行排序。
- 重複放入同一階段、多個同型節點、分支回圈或任意程式碼不是已核准首版能力。若使用者需要「多次插入獨立攪拌」，應擴充穩定 node ID 與有界重複契約，不能用固定四節點假稱已涵蓋此需求。
- 拒絕循環、自我依賴、缺失參照、無入口、無上限等待及無法滿足的必要依賴。禁止任意 Jinja/Python/JS 或任意 HA service 注入流程規則；動作僅為本整合允許的階段。
- 流程/星期編輯預設下一輪生效；每輪綁定明確 revision。總/子開關關閉、急停及收緊安全上限仍需即時阻擋後續物理開啟，不能被已擷取的舊計畫覆蓋。
- 已開始的安全停止與資源釋放不依賴 Card 在線。HA 重啟不盲目續藥，仍沿用先前安全設計方向。

### 略過與依賴必須明示

- 子開關 OFF 或星期不允許，可得到 `skipped_disabled` 或 `skipped_weekday`，不是成功完成。
- **純排序依賴**可以明確選擇略過後接下一個合法步驟，讓不同星期自然形成不同有效流程。
- **必須實際完成／實際開始的依賴**不能用被略過節點假造完成或開始事件；必要條件無法滿足時顯示 `blocked_dependency`，不盲目續跑。
- UI 應預覽七種星期下的有效流程，標出哪些日子會無階段可執行、失去必要混合或出現無法觸發的依賴。避免「星期可以勾，但當天永遠跑不到」的隱性問題。
- 實際資料品質與灌溉許可仍獨立判定；畫面上的排序略過不能代替水質合格。

## 5. 每階段星期：允許條件，不是排程器

- 補水、加養、加酸、獨立攪拌各自具有星期一到日複選；沒有硬編碼「加養僅一/二/五/六」。原星期只可作可選的相容範例，不是所有使用者的出廠限制。
- 全選＝每天；空集合＝沒有允許日，UI 明示「此階段沒有可執行日」，不能把空集合偷偷當每天。[S6]
- 外部呼叫整輪後，後端才判斷各階段的子開關與星期，建立／更新有效執行狀態。
- **建議**以 HA 時區、各階段實際開始前的當地星期檢查，包含等待資源後的再次檢查；不是只在整輪最初檢查一次。執行中跨午夜不因換日突然停泵，仍由安全停止與期限管理。這些細節待 R03 明確核准及測試。
- 替代方案是整輪受理時固定當日資格，優點為跨午夜計畫不變，缺點為階段可能在使用者未勾選的次日開始。獨立研究對此有不同建議，不能假稱平台或研究已替使用者決定；本文件偏向實際階段開始檢查，R03仍待確認。
- 不允許的星期不等待到下個允許日，也不建立長達數天的隱藏排程。其結果為略過或依賴阻擋，由已保存的依賴語意決定。
- 單階段與外部啟動不默認繞過星期。若要保留舊「手動忽略星期」能力，需提供明確一次性選項與授權/記錄；它不是目前已核准的預設，更不能繞過總開關或安全 gate。
- **外部若只在週一呼叫一次，就不會因週二允許加酸而自動在週二啟動。**需要哪些日期呼叫整輪，由使用者的外部排程設定。

## 6. 外部啟動契約（示意，尚不存在於 P1）

HA 官方支援 integration 註冊原生 action/service，讓自動化、腳本、Dashboard 與開發者工具呼叫；整輪作用於每槽 config entry，建議使用必填 `config_entry_id` 與原生選擇器，而不是拿任意品質 Sensor 冒充控制目標。[S1,S6,S7]

```yaml
# 設計示意，P1 尚未註冊此服務，不能直接執行
# 外部 Scheduler / HA 自動化在需要時呼叫
# UI 透過本整合的 config entry selector 選擇槽，不要求使用者手填內部 ID
action: uninus_nutriculture.start_flow
data:
  config_entry_id: "<由前台選擇的養液槽設定項目>"
```

必要契約：

1. 目標必填，校驗屬於本整合且已載入，禁止默認第一槽或全部槽。Core 2026.10.4的async_get_config_entry helper在ID為None時可能選取唯一已載入entry，因此schema必須先拒絕缺值/null，不能只依賴helper。[S7,S8]
   - 設定項目屬於本整合不等於呼叫者有控制權；一般domain service不自動取得Entity service的權限檢查。需決定管理員專用或明確檢查受控Entity原生權限，並傳遞call.context；沒有user_id的合法內部automation不能一概當未授權。這項權限政策納入R04。[S9]
2. 受理前確認總開關、故障/急停、流程版本、可用階段及安全條件；服務不能自動打開總/子開關或更改流程設定。
3. 呼叫成功表示**請求已受理**，不表示馬達已開、流程已完成或水質已合格。建議SupportsResponse.OPTIONAL，僅call.return_response時傳JSON受理/run ID回執，否則None，讓不要求response的外部排程也可呼叫；不是只回資料的ONLY。回應前應原子受理並建立後端任務所有權，後續結果由狀態/事件觀察，不等待數小時。[S1]
4. 同槽忙碌時建議明確拒絕新的不同請求，不默默重啟加藥。可選 `request_id` 用於相同請求去重；具體保留期間及範圍待 R04 凍結。
5. 非法目標、停用或不允許執行等錯誤用 HA 原生例外／翻譯提示，不以「回傳error欄位但服務看似成功」掩蓋拒絕。[S1]
6. 全部階段因子開關／星期被略過時，明示無可執行工作；回應/狀態如何區分拒絕與無操作受理待 R04 決定，不宣稱完成或可灌溉。
7. 外部排程整合需確實支援呼叫原生 HA action；不保證任意第三方版本都可直接選到該服務。可透過使用者建立的原生 HA script 作薄轉接，不把該 script 的建立/管理納入本整合。
8. service 在 integration setup 註冊，無已載入槽時仍有可理解的拒絕，不因缺 entry 就成為 unknown action；`services.yaml`、翻譯及原生 selector 必須齊備。[S1]

本研究沒有註冊或呼叫服務。`start_flow` 是提案名稱，不是已交付API；正式命名、schema、權限及回應在 P2 實作前凍結。

## 8. 實作分期建議

- **P2**：總/子開關資料模型、統一 gate、外部 `start_flow` 操作契約與補水安全；未支援階段不可假啟用；凍結版本化計畫/結果模型。
- **P3**：完成四階段的可配置依賴/時序/星期、加藥/混合/仲裁；最小可用流程編輯表單與預覽，不能把核心可配置能力全延到 P5。
- **P4**：配方、外部 action/結果互通與通知、品質/灌溉許可介面；**不再包含內建排程器、排程匯入或旁支管理**。
- **P5**：進階可視化/手機/鍵盤體驗、可選節點畫布、診斷/歷史、多槽與 HACS 實際安裝驗收。非必要高階分支/重複需另確認，不讓任意程式碼越過安全邊界。

## 10. 驗收重點（後續實作）

- 拖曳/按鈕/下拉設定會產生同一個後端計畫，保存/取消/重開與版本衝突真實有效且不致動。
- 可改成多種順序與合法並行，不固定原站weekday/順序；非法圖、不可達依賴及資源衝突有可解釋結果。
- 每階段七日選擇、全部/空集合、不同星期預覽、跨午夜、等待後改日與被略過的嚴格依賴都有測試。
- 原生服務、Card與外部automation呼叫同一gate；缺目標/錯槽/停用/急停/忙碌/重複請求不會誤開泵。
- 服務受理與實際開始/結束/品質分開；Card離線後流程仍由後端管理。
- 沒有內建時刻/cron排程、匯入或修改外部Scheduler/腳本；安全延遲與期限仍完整。
